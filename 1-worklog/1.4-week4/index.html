- Tags and Resource Groups (lab 000027):
 + Each tag is a key/value pair. A resource can have up to 50 user-defined tags, and tags are case-sensitive
 + Step 1: when creating EC2, choose to tag Instances, Volumes or Network interfaces
 + Step 2: filter instances by tag on the Console using the operators =, !=, : (contains), !: (does not contain)
 + Step 3: redo it with the CLI: add tags with aws ec2 create-tags, create an instance with tags using --tag-specifications, filter with aws ec2 describe-instances --filters Name=tag:Environment,Values=Test
 + Step 4: create a Tag based Resource Group to group resources by tag. A group can only include resources in the same Region
- Tag-based access control (lab 000028): tags in a request can be in 3 places, each with its own condition key:
 + Principal tags (aws:PrincipalTag): attached to the calling user or role
 + Resource tags (ec2:ResourceTag, aws:ResourceTag): attached to existing resources, used to control stop, reboot and terminate actions
 + Request tags (aws:RequestTag, together with the key set aws:TagKeys): included in the create request itself, used to require tags at creation
- The 5 policies of lab 000028: EC2 permissions are split by function, and every policy has a condition:
 + ec2-list-read: allows ec2:Describe*, ec2:Get*, only in us-east-1 and us-west-1
 + ec2-create-tags: only allows tagging during RunInstances (condition ec2:CreateAction)
 + ec2-create-tags-existing: only allows the tag Team=Alpha, and the key can only be Team or Name
 + ec2-run-instances: an instance creation request must include the tag Team=Alpha
 + ec2-manage-instances: only allows start, stop, reboot and terminate on instances that have the tag Team=Alpha
 + Test steps: attach all 5 policies to the role ec2-admin-team-alpha, switch to that role, then test each case. Switching to Tokyo shows API Error. Creating an instance with the tag Team=Beta shows Instance launch failed. Changing the tag to Team=Test shows Failed to update tags. Terminating an instance with Team=Alpha succeeds
- Attribute-based access control (ABAC):
 + A single policy is enough for every project: the variable ${aws:PrincipalTag/Project} compares the caller’s Project tag with the resource’s Project tag
 + A Deny is also needed so users cannot escalate their own permissions in 2 ways: changing the resource’s Project tag (ec2:CreateTags, ec2:DeleteTags) or changing their own tags (iam:TagRole, iam:TagUser)
- Permissions boundary (lab 000030):
 + A boundary only sets an upper limit and does not grant permissions by itself. A boundary can only be attached to IAM users and roles, and it must be a managed policy
 + Step 1: create the user ec2-admin with AmazonEC2FullAccess and attach the boundary ec2-admin-restrict-region, which only allows ec2:* in ap-southeast-1
 + Step 2: test in Singapore, EC2 works normally
 + Step 3: in Sydney, a 403 error appears “because no permissions boundary allows the ec2:DescribeInstances action”
 + Step 4: even in Singapore, Auto Scaling and Load Balancer still show Access denied, because these 2 services are not under the ec2 prefix
 + Clean-up: the user must be deleted first before the policy used as the boundary can be deleted
- AWS KMS and envelope encryption (lab 000033):
 + KMS is only used to encrypt keys, and the Encrypt command accepts at most 4 KB. Data is encrypted with an AES-256 data key (DEK), and the DEK is encrypted by the KMS key
 + When storing an SSE-KMS object, S3 calls GenerateDataKey, uses the DEK to encrypt the object in RAM, deletes the plaintext DEK, then stores the encrypted DEK in the object’s metadata. On each read, S3 calls Decrypt to get the DEK back
 + Step 1: create the customer managed key kms-key-encrypt-decrypt, type Symmetric, usage Encrypt and decrypt, choose the key administrators and key users, and enable automatic key rotation
 + Step 2: create a bucket with SSE-KMS default encryption
 + Step 3: record logs with CloudTrail (trail kms-key-cloudtrail) and query the logs with Athena
- Test results of lab 000033:
 + Even after clicking Make public using ACL, the SSE-KMS object still cannot be opened through the public URL because the request must be signed with SigV4
 + The user User-S3 with AmazonS3FullAccess is still blocked because it lacks kms:Decrypt. S3 permissions and KMS permissions are checked separately
 + A presigned URL valid for 2 minutes: while still valid it can be viewed, and after it expires it shows Access Denied
 + Clean-up: disable the key, schedule the key for deletion after 7 days, stop and delete the trail, delete the bucket, user, group, role and policy
- S3 Bucket Key:
 + S3 requests a bucket-level key from KMS and then generates the DEK for each object itself, which reduces KMS calls by up to 99%
 + It only applies to new objects. The encryption context changes from the object ARN to the bucket ARN
 + KMS cost grows with the number of objects, not with data size, so the more small files a bucket holds, the more Bucket Key should be enabled
- Secrets Manager (lab 000096):
 + Step 1: set up the VPC, Bastion Host, RDS MySQL and Fargate with the CloudFormation stack RDSFargate.yml
 + Step 2: create the secret DBSecret of type Credentials for Amazon RDS database, encrypted with the aws/secretsmanager key
 + Step 3: compare 2 ways to connect: the script mysql.oldway.sh hard-codes the password, while mysql.newway.sh DBSecret gets the password with aws secretsmanager get-secret-value
 + Step 4: enable automatic rotation every 30 days with the Lambda smdemo, Single user strategy. After rotation, the old way shows ERROR 1045 Access denied, while the new way can still connect
 + Step 5: Fargate receives the secret through the Task Definition, using ValueFrom pointing to the secret’s ARN
- Choosing where to store secrets:
 + Secrets Manager is for passwords and API keys that need rotation, with each secret up to 64 KB
 + Parameter Store is for configuration: Standard tier 4 KB, Advanced tier 8 KB
 + Applications should keep secrets in RAM and only read them again when an authentication error occurs
- Working environment (labs 000049 and 000087):
 + CloudShell comes with the AWS CLI and SDKs and runs with the permissions of the signed-in user or role. The home directory is only 1 GB, and files uploaded with the Upload button always go to /home/cloudshell-user
 + AWS Toolkit for VS Code (from version 1.73.0): add a connection with the command AWS: Add a New Connection, and IAM Identity Center is the recommended choice. If access keys are used, the keys are written to ~/.aws/
- boto3 with multiple threads:
 + Once created, boto3.client() is safe to use across threads. Sessions and resources are not
 + Each process creates the client only once and reuses it. Do not share one client across processes
 + max_pool_connections defaults to 10. Running 50 threads with a pool of 10 makes connections keep being opened and discarded, and the log shows “Connection pool is full, discarding connection”
 + connect_timeout and read_timeout default to 60 seconds, and for services that need an immediate response they should be lowered
 + 3 retry modes: legacy (sends at most 5 times), standard (sends at most 3 times, with random delay and a retry quota), adaptive (adds a client-side rate limiter)
 + In Config(retries=...), max_attempts is the number of retries, while in ~/.aws/config it is the total number of sends

Week 4 Achievements:

  • Completed 7 CloudJourney labs (000027, 000028, 000030, 000033, 000096, 000049, 000087) on tags, tag-based access control, permissions boundaries, KMS, Secrets Manager, CloudShell and AWS Toolkit, and finished watching the video Learn 97% of AWS in Under 30 Minutes.

  • Know how to use tags to organize resources: tag EC2 at creation, filter by tag on the Console and with aws ec2 describe-instances --filters, and group resources with a Tag based Resource Group.

  • Able to read tag-based access control policies:

    • Require tags at creation with aws:RequestTag and aws:TagKeys
    • Control running instances with ec2:ResourceTag
    • Use ${aws:PrincipalTag/Project} so that one policy works for every project
    • Use Deny to block tag-changing actions (ec2:CreateTags, ec2:DeleteTags, iam:TagRole, iam:TagUser) so that no one can grant themselves extra permissions

  • Understand that a permissions boundary is only an upper limit: the effective permissions are the intersection with the policies attached to the user or role. When seeing the error “no permissions boundary allows”, know that the boundary itself is what is blocking.

  • Able to explain KMS envelope encryption (GenerateDataKey, DEK, Decrypt) and why SSE-KMS objects need both S3 permissions and the kms:Decrypt permission.

  • Know when to enable S3 Bucket Key, and why KMS cost depends on the number of objects.

  • Understand how Secrets Manager rotates RDS passwords with Lambda, why scripts with hard-coded passwords break right after the first rotation, and when to use Secrets Manager versus Parameter Store.

  • Know how to configure boto3 for multithreaded programs: share one client, set max_pool_connections to match the number of threads, lower connect_timeout and read_timeout, choose between standard and adaptive, and avoid stacking retries across multiple layers.
