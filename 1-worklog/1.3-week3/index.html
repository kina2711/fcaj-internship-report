Week 3 Worklog

Week 3 Objectives:

  • Completed 8 CloudJourney labs (000011, 000063, 000064, 000075, 000002, 000044, 000048, 000012) and 3 videos on the main AWS services and IAM.
  • Install AWS CLI v2, configure 2 profiles default and devops, then build and clean up a system of S3, SNS, IAM, VPC and EC2 using commands only.
  • Correctly state the order in which the SDK looks for credentials and the 4 steps AWS uses to sign a request with Signature Version 4.
  • Be able to apply 5 cost-control methods: Service Quotas, IAM policies with Condition, Billing Console Delegation, Budget Action and Cost Anomaly Detection. Be able to write and test 3 policies that restrict by Region, instance type and volume type.
  • Be able to work out independently whether IAM allows or denies a request when all 5 policy layers are involved.
  • Be able to explain AWS STS, IMDSv2 and how to prevent Confused Deputy; move an application on EC2 from access keys to an IAM role and let users sign in through IAM Identity Center.

- AWS CLI (lab 000011): do everything with commands, without opening the Console:
 + Install CLI v2 and configure 2 profiles default and devops. Access keys are stored in ~/.aws/credentials, while the Region and output format are stored in ~/.aws/config
 + S3: create a bucket, copy files, list, delete files and delete the bucket with mb, cp, ls, rm, rb
 + SNS: create a topic, subscribe and publish a notification with create-topic, subscribe, publish
 + IAM: create a group, a user and an access key
 + Networking and servers: create a VPC, subnet, Internet Gateway, route table and security group, then launch EC2
 + Clean up in order: security group, both subnets, route table, detach then delete the Internet Gateway, VPC, and finally terminate the instance
- Order in which the SDK looks for credentials: the SDK stops at the first source it finds:
 + Parameters passed directly to boto3.client() and boto3.Session()
 + Environment variables AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN
 + Profiles that use assume role, web identity or IAM Identity Center
 + The ~/.aws/credentials and ~/.aws/config files
 + Container credentials, then EC2 IMDS
 + Consequence: leftover environment variables take precedence over AWS_PROFILE. To find out which credentials are in use, run aws configure list and aws sts get-caller-identity
- SigV4 signature: the Secret Access Key never travels over the network; it is only used to compute the signature in 4 steps:
 + Build the canonical request, consisting of the method, URI, query string, headers, the list of signed headers and the SHA256 hash of the body
 + Build the string to sign, including the timestamp and the scope ngày/region/dịch vụ/aws4_request
 + Derive the signing key through 4 rounds of HMAC, so this key is only valid for one day, one Region and one service
 + Attach the signature in the Authorization: AWS4-HMAC-SHA256 header. Requests that are more than 5 minutes off from AWS time are rejected
- Service Quotas (lab 000063): soft quotas can be increased on request, hard quotas cannot (for example, Lambda runs for at most 900 seconds). A quota increase request has 3 possible outcomes: Approve, Deny or Partially approve.
- Limiting costs with IAM (lab 000064): write 3 policies, then test each one:
 + RegionRestrict: only allows EC2, RDS and S3 in ap-southeast-1; switching to Tokyo is denied
 + EC2_FamilyRestrict: only allows launching t3.* instance types; choosing t2.micro shows Instance launch failed
 + EC2EBS_Restrict: Deny when ec2:VolumeType is io1; gp3 volumes are still created normally
 + Note: the broad Allow policy must be removed for these narrow restrictions to take effect
- Billing Console Delegation (lab 000075): by default, IAM users cannot access the Billing page even if they have a policy. Steps: the root account enables Activate IAM Access, then the billing:* policy is attached to the user. The policy is named BillingViewAccess but actually grants full access.
- Cost alerts and blocking:
 + Budgets only alert; they do not block
 + Blocking at resource creation time: IAM Condition, SCP, Service Quotas
 + Budget Action is a partial automatic brake: it attaches a policy that blocks permissions or stops EC2 and RDS
 + Cost Anomaly Detection learns the normal spending level and alerts when there is a deviation
 + Tags must be activated as cost allocation tags in Billing, which can take up to 24 hours
- IAM’s 5 policy layers: SCP, resource-based policy, identity-based policy, permissions boundary and session policy. Evaluation rules:
 + Deny by default; a single matching Deny in any layer overrides every Allow
 + SCPs, boundaries and session policies only set the ceiling; on their own they do not grant permissions
 + Within the same account, it is enough for either the identity-based or the resource-based policy to allow; across two accounts, both sides must allow
 + A group is an identity but not a principal, because a group does not send requests itself
- Switch Role (labs 000002 and 000044):
 + Lab 000002 creates AdminRole that trusts the whole account, so OperatorUser needs an additional inline policy AllowSwitchAdminPolicy for sts:AssumeRole
 + Lab 000044 puts the ARN of No-permission-user directly in the trust policy, so this user does not need any extra permissions
 + Add the Conditions aws:SourceIp and aws:CurrentTime to the trust policy: when the conditions are not met, switch role fails
- AWS STS: temporary credentials have an AccessKeyId starting with ASIA, together with a session token and Expiration; long-term keys start with AKIA. An assume role session lasts 1 hour by default and up to 12 hours; if this role in turn assumes another role, the maximum is only 1 hour.
- IMDSv2 (lab 000048):
 + You must call PUT /latest/api/token to get a token before metadata can be read, which blocks SSRF attacks that can only control the URL
 + Containers running on Docker’s bridge network need the hop limit raised to 2
 + Steps in the lab: upload to S3 using an access key, then redo it with the EC2RoleS3Upload role so that no keys remain in the code, then read the role’s credentials via IMDSv2
- Confused Deputy:
 + sts:ExternalId is used for third parties; the value is generated by the third party and fixed per customer
 + aws:SourceArn and aws:SourceAccount are used for AWS services
 + Do not combine these two kinds of keys in the same statement

 + Enable Organizations and Identity Center
 + Create a group, a user and a permission set. Each permission set becomes an IAM role in the assigned account, with a default session of 1 hour

Week 3 Achievements:

  • Completed 8 CloudJourney labs on AWS CLI, cost, IAM, STS and Identity Center, along with 3 videos on the main AWS services and IAM.

  • Used AWS CLI v2 with 2 profiles to work with S3, SNS, IAM, VPC and EC2 and to clean up resources in the correct order.

  • Understood that every action on AWS is an API call signed with SigV4; know how to check which credentials are in use with aws configure list and aws sts get-caller-identity.

  • Able to compare the ways of providing credentials:

    • Long-term access keys are only suitable for personal labs and must be deleted when finished
    • Identity Center is for humans
    • Instance profiles via IMDSv2 are for code running on EC2
    • Web identity via OIDC is for CI/CD

  • Able to distinguish the group that blocks costs at resource creation time (IAM Condition, SCP, Service Quotas) from the group that only alerts after money has been spent (Budgets, Cost Anomaly Detection, CloudWatch Billing Alarm).

  • Able to write the 3 policies RegionRestrict, EC2_FamilyRestrict, EC2EBS_Restrict and know why the broad Allow policy must be removed for them to take effect.

  • Able to work out by hand whether IAM allows or denies a request: look for a Deny first, then check SCP, resource-based policy, identity-based policy, boundary and session policy in turn.

  • Able to explain why lab 000002 needs the additional AllowSwitchAdminPolicy while lab 000044 does not.

  • Understood why applications should use roles instead of access keys:

    • IMDSv2 protects against SSRF with a token and the hop limit
    • STS credentials expire automatically; they cannot be revoked individually, so you have to Deny based on aws:TokenIssueTime
    • Cross-account access requires a trust policy on the role owner’s side and an identity-based policy on the caller’s side
